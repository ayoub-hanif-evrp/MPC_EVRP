## Verified formulation and information boundary

Let the fixed infrastructure be depot `0`, stations `F`, and Desaulniers customers `C`; customer `i` has location, demand `q_i`, service duration `s_i`, and hard start window `[e_i,l_i]`. At decision time `t`, the observable set is `A_t={i:r_i<=t}` minus already committed/served customers. [The observation boundary](../evrp/observation.py) passes `t`, infrastructure, visible customer records and committed-customer IDs to the policy. It does **not** pass the full `Instance`, hidden-customer records, release calendar, reference routes, or a hidden count. [OptimizationContext](../evrp/optimizers/base.py) additionally holds measured vehicle/post-action origins, busy actions, soft future suffixes, known served/committed sets, common constructor routes, `K_ref`, seed, deadline and MPC settings. The simulator retains hidden data privately to advance time and reveal events ([simulator](../evrp/simulator.py)). This code boundary and saved-trace audits support nonanticipation of *specific future requests*; they are not a formal side-channel/security proof.

**Horizon and action.** For the five `MPC_*` fleet methods, a planning epoch optimizes finite vehicle-route suffixes for **all currently released, uncommitted customers**. It is not a forecast of future unknown requests. `MPCConfig.prediction_horizon=5` limits service depth in the separate per-vehicle `MPCPlanningProblem`; the five fleet optimizers use the common fleet constructor and suffix evaluator, and MCTS's depth `4` is search-tree structural-move depth, not four future time periods ([MPC problem](../evrp/mpc.py), [fleet problem and MCTS](../evrp/fleet_mcts.py), [simulator](../evrp/simulator.py), [config](../configs/paper_controller.yaml)). `control_horizon=1`: after candidate suffixes are reconciled and physically replayed, only the first feasible action of each ready EV is dispatched. The remainder is a revisable intent. For busy EVs, planning uses the state **after** the already committed action; dispatch cannot interrupt that action. Serve, travel-to-station/charge, and return transitions run to completion; time advances to the next release, busy completion, or idle-wait event ([simulator](../evrp/simulator.py)). Trigger causes are initial planning, release, infeasible suffix, service completion with uncovered known work, or missing continuation. No probabilistic demand model is used in the original five-method comparison.

**Physical equations.** For an admissible arc `i→j`, `d_ij` is Euclidean length rounded up to the benchmark distance precision, travel time is `d_ij/v`, and consumption is the specified consumption factor times Euclidean distance rounded up to energy precision ([instance](../evrp/instance.py)). Arrival SOC is `B'=B-E_ij>=0`; a charge to target `B*` adds `B*-B'` with duration `(B*-B')·inverse_charge_rate`; the target must exceed arrival SOC and not exceed capacity. The Desaulniers MP parser converts published fuel units into **time-equivalent battery units** (`battery=Q·r`, `consumption=r`, `inverse_charge_rate=1`, `speed=1`) and checks rounded arcs and permitted topology against paired format-2 files. These are benchmark units, not calibrated kWh or real-road minutes. The converter rejects station-to-station arcs for this published format ([instance](../evrp/instance.py), [transition](../evrp/model.py)). Multiple partial station charges are permitted, subject to positive gain and physical replay. At a customer, start `S_i=max(arrival_i,e_i)` must satisfy `S_i<=l_i`; service ends `S_i+s_i`, capacity decreases by `q_i`, and the depot/station windows also constrain transitions. Every accepted action must retain a feasible station/depot escape by depot closing time. [Route replay](../evrp/repair.py) and the optional [resource-label decoder](../evrp/resource_decoder.py) enforce these constraints. Bounded decoding can miss feasible routes; a decoder rejection is not a global infeasibility proof.

**Common optimization objective.** At epoch `t`, let `U` be uncovered *visible* work after choosing suffixes. [FleetObjectiveEvaluator](../evrp/optimizers/objective.py) minimizes a lexicographic tuple, not a single distance sum. When `U≠∅`: `( |U|, screened_zero_options, screened_one_option, control_risk, TW_risk, battery_risk, capacity_risk, normalized_distance )`. When all visible work is covered: `(0, control_risk, flexibility_risk, activated_EVs, operational_cost, distance, route_instability)`. The screening/risk terms are heuristic plan scores; only replay establishes physical feasibility. This is an **epoch-level** objective. It does not guarantee that minimizing uncovered visible work at each epoch maximizes final online service. `K_ref` is fixed across methods and comes from an offline feasible schedule. It is legitimate known exogenous fleet capacity in this study, but its reference-dependent choice makes the scenario design conditional on an offline witness; the optimizer never receives the reference route or unreleased customer identities.

## Dynamic benchmark: validity and scope

The [Desaulniers et al. 2016 MP EVRPTW paper](https://doi.org/10.1287/opre.2016.1535) supplies static EV instance structure, not a native online arrival process. The parser checks paired benchmark coordinates/arc semantics ([instance](../evrp/instance.py)); [reference validation](../evrp/reference.py) independently replays each route with the common transition engine and checks every customer served exactly once and every vehicle returned. The 2016 paper and the repository's custom dynamicization should be cited separately.

For reference route `R`, let `p(i)` be the predecessor action of customer `i` and `D^R_{p(i)}` its departure time. The generator sets `b_i=min(e_i,D^R_{p(i)})`; eligible `b_i>0` requests chosen as dynamic get `r_i=(1-U_i)b_i`, `U_i∼Uniform(0,1)`, while others get `r_i=0` ([scenario](../evrp/scenario.py)). Hence `0<=r_i<=b_i<=e_i`; each chosen request is revealed **before its earliest time-window service start** and no later than the reference predecessor departure. The exact reference route can therefore still be followed with full foresight and the same `K_ref=|R|`. This is a feasible witness, not necessarily a minimum-fleet or minimum-cost optimum. Online policy cannot follow unknown future customer records; an early physical commitment can make later visible work unreachable. Offline 100% feasibility does not imply an online 100% guarantee.

This is closely related to, and should accurately credit, [Yang et al. (2017)](https://doi.org/10.1007/s11047-016-9550-9): their **theoretical Solomon-derived benchmark** also samples availability in `[0,min(e_i,t_{i-1})]` using departure in a best-known static schedule, with dynamicity as the probability of nonzero availability. Their *field incident* availability instead equals the incident window start. The repository applies the theoretical bound to Desaulniers MP data and, in the paper protocols, selects an **exact count** `round_half_up(DoD_target·|C|)` from eligible requests. Realized DoD is `#{r_i>0}/|C|`; it equals the target only when the count is representable and eligibility suffices. `bernoulli` mode instead draws each customer with target probability then intersects eligibility, so realized DoD can be lower. These distinctions and the event-driven replanning model should be explicit. The reference-derived announcement lead time and guaranteed clairvoyant witness deliberately structure the online problem. They do not prove that each instance is easy for an online policy, but they exclude late-after-window and intrinsically infeasible arrivals by construction.

**Separate unimplemented stress regime (proposal).** Freeze new geometry or a disclosed customer pool and physical parameter set *without building release times from a solution*. Predeclare independent parent seeds, locations/demands/windows, fixed fleet policy from training-side public metadata, and an arrival process `N(t)` with prespecified intensity levels (e.g., low/medium/high). Independently sample announcement lead `L_i` from a disclosed distribution (including `L_i<=0` if late announcement is explicitly in scope), then set `r_i=e_i-L_i` clipped only to the study start—not to a reference predecessor. Expose only released records. If using existing static customer locations, disclose parent reuse and label the test **stress on exposed geometry**, not independent confirmation. Keep exactly the same travel, charging, load, time-window and return rules for all five methods. A new schema would be needed to permit `r_i>e_i`; no code or existing benchmark is changed here. Report (a) all announced demand as denominator, (b) customers with a rigorous necessary-condition impossibility certificate at reveal (e.g., release after due, no physically reachable service/return path), (c) unresolved feasibility cases, and (d) independently verified full-information witnesses where available. Never call a bounded heuristic failure proof of impossible service; do not drop hard cases from service rates. Stratify by lead time, arrival intensity, and demand origin. This is a different estimand from the reference-preserving main study.

## Comparator identity and novelty

| Method | What this code actually does | Relationship to prior art |
| --- | --- | --- |
| `MPC_COMPLETION` | Returns the common constructor's validated suffix without further search ([code](../evrp/optimizers/completion.py)). | Internal no-search control; constructor itself includes insertion/repair, so it is not a trivial greedy benchmark. |
| `MPC_MCTS` | Searches structural fleet suffix moves using progressive widening/UCT-like value-plus-prior selection, rollouts, root-control evidence and incumbent validation ([adapter](../evrp/optimizers/mcts.py), [tree](../evrp/fleet_mcts.py)). | An EV routing adaptation of established MCTS concepts; see [Browne et al. 2012](https://doi.org/10.1109/TCIAIG.2012.2186810). It does not simulate hidden future requests. |
| `MPC_ALNS` | Selects among several destroy/repair operators with adaptive segment weights, uses service-preserving/current-score acceptance and a bounded simulated-annealing rule among equal-service plans; returns best validated incumbent ([code](../evrp/optimizers/alns.py)). | Adaptation of [Ropke and Pisinger 2006 ALNS](https://doi.org/10.1287/trsc.1050.0135), with repository-specific EV decoding and score. Not the authors' official solver. |
| `MPC_HGS` | Maintains a small population, service-first objective/diversity ranks, tournament parents, route crossover, local education, diversification and survivor selection ([code](../evrp/optimizers/hgs.py)). | HGS-inspired custom implementation, distinct from [Vidal's published HGS-CVRP](https://doi.org/10.1016/j.cor.2021.105643) and not verified as equivalent to it. |
| `MPC_ACS` | Constructive ants choose feasible insertions by pheromone×heuristic desirability, with exploitation probability, local evaporation and global best deposits ([code](../evrp/optimizers/acs.py)). | ACS-inspired custom insertion search; [Dorigo and Gambardella 1997](https://doi.org/10.1109/4235.585892) and Yang et al. predate this. It is not a verified reproduction of MACS-VRPTW. |

All five share the same observation boundary, physical transition/replay, fleet constructor, lexicographic evaluator, fixed fleet, and decision budget ([simulator](../evrp/simulator.py), [objective](../evrp/optimizers/objective.py)). Shared infrastructure is a **controlled comparison design and software contribution**, not a new optimizer theorem. The adaptation to Desaulniers MP physics and the archived paired audits are reproducibility contributions; noninterruptible execution and partial charging are important modeling choices but have published antecedents ([Desaulniers 2016](https://doi.org/10.1287/opre.2016.1535), [Schneider et al. 2014](https://doi.org/10.1287/trsc.2013.0490)). Do not claim first use of MPC, online EV routing, multiple charging, ALNS, HGS, ACS, MCTS, or irreversible dispatch. A comprehensive novelty review would require a wider systematic literature search; this audit finds **no supported new algorithmic claim**.

Negative repository evidence must remain visible. [Stable V3](../results/desaulniers/publication_development/stable_screen_v1/RESULTS.md) served 98.29% versus original ALNS 98.38% on 18 development scenarios; [targeted service study](../results/desaulniers/targeted_service_v1/FINAL_REPORT.md) did not promote urgency/resource/first-action variants; [SLAD V1/V2](../results/research_v2/slad_feasibility_v2/validation/RESULTS.md) found two equal-service suffix swaps but no additional coverage or changed ready action; and the [two-case original-method pilot](../results/research_v2/mpc_reliability_v1/validation/RESULTS.md) had MCTS below Completion on R101 (87 versus 89). These are not new independent final comparisons.

## Existing experimental evidence: supported versus unsupported

The frozen [primary paper report](../results/desaulniers/final_cpu_paper_v1/PAPER_RESULTS.md) has 90 paired scenarios, 450 method runs, six parents and five release seeds at three target DoDs; the separate replication has 12 scenarios, 60 runs, six other parents, DoD 0.50 and two seeds. Saved audits independently replayed **510/510** physical/information/deadline records ([validation](../results/desaulniers/final_cpu_paper_v1/audit/VALIDATION.md)). Primary service/complete-service: Completion **87.35%, 40/90**; MCTS **92.84%, 45/90**; ALNS **98.95%, 63/90**; HGS **97.47%, 58/90**; ACS **95.98%, 49/90**. Replication: Completion **90.57%, 4/12**; MCTS **93.86%, 7/12**; ALNS **98.71%, 6/12**; HGS **97.14%, 6/12**; ACS **97.14%, 7/12**. These are observed cohort summaries, not universal rankings.

**Estimands and uncertainty.** The primary MCTS–Completion customer-weighted difference is **5.486 percentage points** with exploratory parent-cluster percentile interval **[0.827, 8.074]**; the parent-equal mean difference is **4.067 pp [1.178, 7.244]**. They answer different weighting questions. Primary ALNS–HGS is **1.486 pp [-0.467, 2.489]** customer-weighted and **0.633 pp [-0.622, 1.944]** parent-equal; neither interval establishes superiority. Complete-service scenario differences must use paired binary indicators, not interpret 98.95% served as 98.95% fully served. The [two statistical tables](../results/desaulniers/final_cpu_paper_v1/tables/primary_endpoint_paired_statistics.md) retain all contrasts. Six parent clusters yield fragile intervals; families are represented by one parent each in the primary cohort, and multiple method contrasts/subgroup views have no familywise error control. Parent exposure and prior development work prevent describing an additional Desaulniers seed/size as untouched. The historical 270-run holdout, 450-run robustness, 60-run replication and development screens use different protocols and must remain separate ([limitations](../results/desaulniers/final_cpu_paper_v1/LIMITATIONS.md)).

**Fairness judgment.** Within each frozen scenario the five original identities receive the same published physics, release schedule, `K_ref`, observation, constructor, lexicographic objective, and five-second decision budget. This supports a fair comparison of **repository adapters inside one controller**, not a tournament among official standalone solvers. Different algorithms have different computational effort and cooperative deadline behavior; report p50/p95/p99/max decision latency plus worker CPU/wall time separately. The reported 10.04 primary worker-hours and 1.80 replication worker-hours are sums of run time, not per-decision latency or an isolated hardware speed test. All recorded decisions were under five seconds, but this is not a strict worst-case real-time proof. The versioned safe-initialization policy is an operational correction, not part of original historical outcomes; original HGS/ACS/ALNS timeout defects remain. Conditional distance/energy statements require identical served sets; jointly complete cases (39 primary scenarios) are selected on outcome and limit interpretation. Report all negative cases and failed attempts.

### Claims to revise or remove

1. Replace “novel ALNS/HGS/ACS/MCTS algorithm” with “five custom optimization adapters evaluated under a common event-triggered EV fleet MPC controller.”
2. Replace “predicts future requests” with “replans on releases and other events using currently observed requests.”
3. Replace “100% service is achievable online” with “a clairvoyant reference serves all requests; online information is restricted.”
4. Replace “ALNS is significantly best” with “ALNS has the highest observed service in the reported cohorts; ALNS–HGS parent-cluster intervals include zero.”
5. Replace “five-second real-time guarantee” with “observed decision latencies in audited runs were below five seconds under a cooperative budget.”
6. Remove unconditional operating-efficiency rankings across methods serving different customer sets, and any claim that the 90 scenarios are 90 independent benchmark geometries.

## Verification record and final judgment

The local test assertion now expects shared `NameError` with a `best`/local-variable diagnostic; it continues to exercise the original uninitialized-incumbent defect and the separate `MPC_ALNS_SAFE_INIT_V1` correction. Python 3.12 targeted pytest passed. The full Python 3.12 suite passed **526 tests, 4 skipped** in the unsandboxed rerun. The first local full-suite attempt under the Windows filesystem sandbox hit pytest temp-directory permission errors, not optimizer assertions. An available Python 3.11 runtime lacked pytest, NumPy and SciPy. A direct Python 3.11 execution of the **same expired-context behavior** confirmed `NameError` naming `best` for the original and `OptimizerInitializationDeadline` for the safe variant; the exact pytest target could not run there because its dependencies were unavailable. An isolated dependency installation was attempted but its scientific-package download stalled and was stopped; temporary test dependencies were removed. No commit/push was made under this task's restriction, so **green GitHub CI on the corrected revision is still outstanding**.

**Judgment: not yet suitable for submission as currently claimed.** A narrowly framed, reproducible comparative-computation paper is scientifically defensible **with revisions**: correct CI, narrow claims to the reference-preserving Desaulniers setting, disclose six-parent uncertainty and prior exposure, and present the five methods as custom adapters. A new optimizer invention, universal ALNS superiority, arbitrary-arrival robustness, or certified real-time operation is not supported. Stronger external claims require new independent parent geometry.

# V3A benchmark provenance and scope

## Dataset A (required, installed)

Source: [Bruglieri–Moreschini EVRPTW-CPS-MRT data](https://github.com/lmores/or-evrptw-cps-mrt-data), Git commit `c79f4c53a4b18f722a1047f089f811a3bb1ffaa0`, GPL-3.0. The 224 original JSON files (12,668,753 bytes) are held in ignored `data/third_party_v3a/or-evrptw-cps-mrt-data/`; their individual SHA-256 digests are in [DATASET_A_MANIFEST.json](DATASET_A_MANIFEST.json). Both the 224 original imports and 224 derived one-charger imports pass structural validation. The repository README uses camelCase field labels, but actual JSON keys are snake_case. The adapter reads the real keys and uses `travel_distances`/`travel_times`, never coordinates, for travel physics.

The derived fixture keeps the first charger of each station and removes all other station chargers, keeping charger-specific windows, costs and profiles aligned. It is explicitly named `_derived_1ch`; the original file remains untouched. The pilot's dynamic releases are generated by a prespecified rule, since Dataset A is a static benchmark. This derived online scenario must not be called an official dynamic instance.

The official JSON describes a depot recharge **cost** but no depot charging time or limited depot charger capacity. V3A currently assumes instantaneous depot battery refill and load reload at return, paying the provided cost. This assumption sharply limits charger contention in the pilot and is stated in its protocol and findings. The simulator's public-station charging rates and availability are taken from the official profiles and windows.

Local verification:

```powershell
git clone https://github.com/lmores/or-evrptw-cps-mrt-data.git data/third_party_v3a/or-evrptw-cps-mrt-data
git -C data/third_party_v3a/or-evrptw-cps-mrt-data checkout c79f4c53a4b18f722a1047f089f811a3bb1ffaa0
python -m scripts.research_v3a.verify_dataset
```

Redistribution of the upstream files is avoided in this project; users acquire them from the attributed upstream GPL-3.0 repository.

## Dataset B (conditional, not downloaded)

[Zenodo record 18529191](https://zenodo.org/records/18529191) describes 20 North American territories and 1,600 semi-synthetic daily EVRPTW instances at customer scales 5/15/50/100. Its page identifies release v1.1 while the sole 527.7 MB archive is named `EVRP-TW-D-B-v1.0.tar.gz` with MD5 `7cc5ddd617dff8792b167f45ab7e4ed3`. Its Rights/License field is blank in the public record. The record does not resolve the archive naming discrepancy or establish redistribution terms, so Dataset B was not downloaded or substituted into V3A. Territory-level split and schema verification must follow a resolved release/rights statement and a checksum-verified safe extraction. [Zenodo's permission guidance](https://support.zenodo.org/help/en-gb/2-content/21-can-i-get-permission-to-use-a-specific-record) makes record-specific rights relevant; an absent field should not be assumed to mean CC-BY.

## Dataset C (optional, not downloaded)

The supplied DOI `10.5281/zenodo.19443014` could not be resolved through the available official record interface during this task. License, checksum, size and schema therefore remain unverified. Dataset C was not used. A static waiting-time attribute would not substitute for endogenous queue simulation even if obtained later.
